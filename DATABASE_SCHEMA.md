# DATABASE SCHEMA: FIN-LIT
## Prisma ORM Data Model Specification

Fin-Lit implements a fully normalized relational data model enforcing strict user isolation and referential integrity.

---

### Entity Relationship Summary

| Model | Purpose | Key Relations |
|---|---|---|
| `User` | Core user identity, contact details, currency | One-to-One: `UserProfile`, `FinancialProfile`. One-to-Many: all financial assets |
| `UserProfile` | Occupation classification (Student vs Professional), income, frequency | Many-to-One: `User` |
| `FinancialProfile` | Savings target, target type, financial health score, risk tolerance | Many-to-One: `User` |
| `IncomeSource` | Inflow streams (salary, allowance, freelancing, scholarship) | Many-to-One: `User` |
| `TransactionCategory` | 12 default Indian categories + custom categories, icon, color | One-to-Many: `BudgetAllocation`, `Transaction` |
| `Budget` | Monthly budget container (`YYYY-MM`), total income, allocated, spent | One-to-Many: `BudgetAllocation`, `BudgetTransfer` |
| `BudgetAllocation` | Individual category limits and spent counters | Many-to-One: `Budget`, `TransactionCategory` |
| `BudgetTransfer` | Audit trail of approved AI budget reallocations | Many-to-One: `Budget`, `fromAllocation`, `toAllocation` |
| `Transaction` | Unified ledger entry (amount, merchant, category, UPI ref, status) | Many-to-One: `User`, `TransactionCategory`, `PaymentSource` |
| `PaymentSource` | Connected UPI apps (GPay, PhonePe, Paytm, BHIM) and bank accounts | Many-to-One: `User`, One-to-Many: `Transaction` |
| `Subscription` | Recurring subscriptions (Netflix, Spotify, Gym) and renewal dates | Many-to-One: `User`, `TransactionCategory` |
| `SavingsGoal` | Milestone targets (Emergency Fund, Travel, Gadgets) and saved amounts | Many-to-One: `User` |
| `Notification` | In-app alerts (budget thresholds, renewals, daily summaries) | Many-to-One: `User` |
| `AIInsight` | Proactive observations generated by the analytics layer | Many-to-One: `User` |
| `AIRecommendation` | Actionable proposals (reallocations, savings boosts) awaiting user approval | Many-to-One: `User` |
| `ImportedStatement` | Audit of ingested CSV files with duplicate counts | Many-to-One: `User` |
| `AuditLog` | Security logging of sensitive user operations | Many-to-One: `User` |

---

### Key Schema Design Decisions

1. **Deterministic Unique Constraints**:
   - `Budget`: `@@unique([userId, month])` guarantees exactly one active budget per user per month.
   - `BudgetAllocation`: `@@unique([budgetId, categoryId])` guarantees clean allocation lookups.
   - `Transaction`: `idempotencyKey String? @unique` ensures bank statement imports and UPI syncs never produce duplicate records.
2. **Precision Representations**:
   - Monetary amounts are stored as floating point numbers mapped strictly in Indian Rupees (`INR`), with deterministic 2-decimal rounding in the application layer.
3. **Data Isolation**:
   - All financial records contain a non-nullable `userId` foreign key with cascade deletion on user removal.
